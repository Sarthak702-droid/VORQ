VORQ | Frontend Engineering and Reuse Specification
Implementation handbook v1.0 | 03 November 2026 | Reuse-first delivery
# 1. Frontend engineering decision
Primary customer-facing UI = existing BuildSuite Core frontend (Vue + Vite; verify exact packages in pinned revision), branded and extended with a single VORQ shell. Frappe Desk remains an intentional specialist workspace for accounting, tax administration and setup. New mobile site PWA flows should reuse components, composables and REST data contracts from BuildSuite where feasible. Do not create an entirely new Next.js frontend just because the team has Next.js experience.
OpenConstructionERP uses React + TypeScript + Vite and is a potential future specialized tool surface, not an excuse to move all v1 modules into React. OpenProject uses its own UI stack and should be API-integrated only after product need is proven. In production, each authorized user sees one coherent product, not five login screens.
# 2. Mandatory discovery before coding

Top bar: VORQ wordmark, tenant/company name, project selector, alert count, help, profile and network state. Sidebar: Home, My Projects, Site, Materials, Labour, Procurement, Subcontracts, BOQ, Finance, Reports and Settings. # 6. Permission-aware navigation pattern

// Illustrative contract, not a copy of BuildSuite source code
interface SessionContext {
  companyId: string;
  userId: string;
  assignedProjectIds: string[];
  capabilities: string[];  // populated by server
}

const menuItems = [
  { key: 'home', path: '/home', permission: 'home.read' },
  { key: 'boq', path: '/projects/:id/boq', permission: 'boq.read' },
  { key: 'finance', path: '/finance/overview', permission: 'finance.read' },
];

function visibleMenu(session: SessionContext) {
  return menuItems.filter(item => session.capabilities.includes(item.permission));
}
// This controls presentation only. Back-end APIs must verify permission and project 
scope.
Capabilities should be derived by authenticated backend from Frappe roles + project memberships + feature plan + approval threshold. Never trust user-editable localStorage for a permission decision. Deep links must 403 cleanly if access is absent, not crash or leak data.
# 7. Frontend data service standards
Use one API client abstraction per business module with typed request/response shapes. Prefer official upstream Frappe REST/RPC and existing BuildSuite API client conventions.
An API result is not assumed to be valid; validate critical response fields, doc status, currency and per-project scope.
Use server-generated summaries for expensive financial aggregation; do not fetch thousands of GL entries to compute totals in the browser.
Separate authoritative remote state from ephemeral local form state. Normalize errors into permission denied, validation error, conflict, network error, server error and unavailable feature.
Use request IDs on mutations, disable duplicate submit while in flight, preserve retry semantics and render confirmed ERP doc reference after success.
Never optimistically set invoice as paid, PO as approved or stock quantity as consumed until source record is confirmed by backend.
Date/time: store ISO 8601 timestamps with timezone; render Asia/Kolkata in UI as appropriate; do not use unqualified local-date strings for cross-service ordering.
Monetary calculation: use integer minor units or precise decimals in computation; avoid floating-point summation for booked totals. UI rounds only for display.
# 8. Screen-specific frontend requirements
## 8.1 Portfolio and project dashboards
Define KPI types with sourceDocTypes, asOf, taxBasis, status and drilldownURL. A null KPI renders 'Not available', not 0. Skeleton loading maintains fixed card height. Source-backed cost categories must reconcile to Frappe server. Owner can filter by current projects but cannot view other companies' data.
## 8.2 BOQ editor
Use existing BuildSuite grid/tree first; build a column adapter for code/description/UOM/quantity/rate/amount. Validate uploaded CSV/XLSX preview row by row and surface duplicate codes, invalid UOMs and impossible values. Maintain dirty-state warning, revision compare and approval lock. Advanced OpenConstructionERP AG Grid is gated by legal and feasibility review; copy neither the whole app nor its AGPL frontend without approval.
## 8.3 Materials
Provide idempotent POST for material issue and source link; show lifecycle tabs and transaction detail. An edited draft may be saved locally; approved receipt/issue remains server-authoritative. For site use, provide oversized controls and barcode/manual item selection only if customers validate need. Avoid generalized warehouse management rewrite.
## 8.4 Labour and field reports
Prioritize select-crew, mark exceptions, enter shift, attach photo and save. Group submissions per project/site/date with deterministic draft key. Show server rejection with field path, not generic toast. If user changes project while draft exists, prompt save/discard without losing data.
## 8.5 Finance
Read-only summary can use custom VORQ dashboard; detailed invoices and reconciliation go to Frappe Desk deep links. Preserve common customer header and back navigation. Display GST/withholding only based on approved accounting configuration; no client-side guessed tax.
## 8.6 Approval workflow
Review details and linked evidence before action. UI enforces eligibility for convenience; server enforces threshold, role and maker-checker rule. An approval action returns final doc status and version. Conflicts show updated record and re-open rather than overwriting server state.
# 9. Offline PWA implementation specification
## 9.1 PWA constraints
A PWA is not identical to a native Android app. Do not promise indefinite offline operation, large background uploads when closed, or guaranteed sync under battery restrictions. Do not cache payment details, journal records or broad customer lists on device.
## 9.2 Offline draft lifecycle
Online authenticated user opens assigned site and downloads permitted minimal reference data.
User fills daily report and photo attachments; locally save draft in IndexedDB with project/date/user/revision and retention expiry.
When offline, show amber 'Saved on device; not submitted' and pending queue count.
On reconnect, check session validity and project membership; upload attachments in bounded chunks/retries where supported.
POST report with clientDraftId and idempotency key. Backend returns canonical server doc ID and confirmed status.
Mark local item synced only after confirmed response; clear private payload based on retention policy. Conflict shows explicit merge/review screen.
## 9.3 Safe queue object

interface OfflineSiteDraft {
  localId: string;
  tenantSite: string;
  projectId: string;
  siteDate: string;
  formVersion: number;
  status: 'draft' | 'pending' | 'conflict' | 'failed' | 'synced';
  lastEditedAt: string;
  idempotencyKey: string;
  payloadRef: string; // IndexedDB pointer, not URL containing secrets
}
Test airplane mode, browser kill, duplicate reconnect, session expiry, role revoked while offline, storage cleared, upload interruption and conflicting amended report. Offline records must not silently move to submitted or approved.
# 10. Specialized engine integration UI
## 10.1 OpenProject
Before integrating, prove OpenProject API v3 supports the exact work package, dependency, schedule and user operations needed. If not, keep BuildSuite scheduler. If enabled, maintain canonical project/task mapping and show remote update/failure state. Never present parallel editable task stores without authoritative owner.
## 10.2 OpenConstructionERP
Implement only after license review and proof-of-value. OpenConstructionERP's React frontend can be deployed as a separate tool with SSO and mapped VORQ theme tokens, or selected components may be legally reused under compliant terms. React components cannot simply be imported into Vue like local single-file components; choose a routed microfrontend/wrapper with strict postMessage or API contracts if necessary. Avoid raw cross-origin iframe without session, CSP, accessibility, and security review.
## 10.3 Cepho
Do not mount Cepho v15 screens into a v16 installation. Use its business workflow as a tested design reference for client progress billing and port the minimal needed interface into compatible BuildSuite/Vue views with consistent design.

# 12. Definition of done by frontend module
A module is complete when it uses actual API data, respects project/tenant access, has coherent app-shell integration, supports keyboard/mobile interaction, shows accurate loading/error/empty/sync states, has tests for 403/409/5xx and duplicate mutation, records meaningful usage analytics without sensitive data, and passes sign-off from the business-role owner. Screenshots alone are not proof.

# 14. Explicit DON'T list
Do not rebuild all of ERPNext in React or Next.js.
Do not pretend BuildSuite beta UI has no dormant/mock routes; audit actual source.
Do not combine incompatible Vue, React and Angular components by copying files into one directory.
Do not switch authentication providers without an explicit centralized identity migration plan.
Do not let UI route filtering replace server permissions.
Do not expose personal access tokens/API secrets in source, network logs or local storage.
Do not persist posted accounting documents in offline queues.
Do not implement finance totals with JavaScript float accumulation over pagination.
Do not hide 403 or sync failures as empty success states.
Do not introduce visual redesign churn before core contractor tasks pass usability testing.
Do not use mock data in production or label unsupported forecasts as actual profits.

# 17. Final engineering acceptance gate
A first-time contractor user can log in on desktop or mobile, see only their authorized company/project, enter a site day's activity, process material and labour through real source documents, inspect valid project financial status and recover gracefully from network/permission errors. No software-vendor seam, incorrect money status, duplicate accounting document, inaccessible mobile control or AGPL licensing blind spot may be waved away as a 'frontend polish task'.
