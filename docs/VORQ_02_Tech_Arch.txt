VORQ | Technology Stack and System Architecture
Engineering specification v1.0 | 03 November 2026 | Implementation planning reference
# 1. Architecture decision in one page
VORQ shall reuse a functioning ERP rather than reproduce ERP internals. The primary runtime is Frappe Framework v16 + ERPNext v16 + BuildSuite Core compatible pinned revision, plus a small VORQ integration/customization app. The production database of record for construction transactional and accounting data is MariaDB within each Frappe customer site. Redis and background workers support queues/caching. BuildSuite's existing frontend and Frappe Desk are first-class reusable interfaces. A separate Next.js backend or Convex database is NOT required for the initial release.
Important boundary: one product does not require every vendor's code in one process or every service in one database. OpenProject and OpenConstructionERP should remain isolated optional engines behind contracts. Cepho is an idea/reference source first, not a production-installable sibling of BuildSuite on the same v16 site unless code porting is proven.

Purchase receipt, stock and material transactions	ERPNext stock documents	BuildSuite captures intent / validates source link

No dual-write of ledger records from two separate apps. When a source generates a target document, use source ID + target ID + unique constraint + transaction boundary. Events can trigger asynchronous read-side refreshes, not competing ledger writes.

# 7. Authorization and tenant safety
Customer tenancy starts with one Frappe site and database per organization; do not share rows across customer sites in a custom global service.
Authenticate with Frappe-managed secure sessions. Use server-side role and project checks on every endpoint. Use CSRF protection for authenticated browser writes; never expose API secrets to browser JavaScript.
Support owner, PM, QS, Site Engineer, Storekeeper, Procurement, Accountant, external Subcontractor and operator roles. Permissions are additive only when explicit; sensitive financial operations need maker-checker approval.
Project scoping applies to lists, record read, reports, attachments, search, exports, background jobs and websocket subscriptions.
When adding OpenProject/OpenConstructionERP, establish SSO or trusted proxy authorization plus synchronized project scope; do not silently pass end-user ERPNext tokens to external services.
Customer support must use time-bound, logged break-glass access approved by authorized tenant administrators.
# 8. Integration contracts and failure semantics
## 8.1 VORQ domain adapter interface

CreateProject / GetProject / ListProjects
ImportBOQDraft / ApproveBOQRevision
CreateMaterialRequest / ReceiveGoods / PostMaterialIssue
SubmitDailySiteReport / SubmitLabourMuster
SubmitSubcontractMeasurement / ApproveSubcontractBill
GetProjectCostSnapshot / GetReceivablesPayables
CreateClientMilestoneInvoice / GetLinkedERPDocument
Each request carries tenant context from authenticated host, user context, canonical project ID, request ID, idempotency key for writes and expected revision for edit conflicts. The server validates permissions and state transitions; input shape alone is not authorization.
## 8.2 Example cost snapshot contract

{
  "project_id": "PRJ-001",
  "as_of": "2026-11-03T16:00:00+05:30",
  "currency": "INR",
  "budget_ex_tax": 8000000,
  "actual_posted_ex_tax": 4800000,
  "open_commitments_ex_tax": 900000,
  "forecast_to_complete_ex_tax": null,
  "data_quality": "incomplete_forecast",
  "source_documents": 214
}
A blank forecast is deliberately null rather than a fabricated number. Tax-inclusive vs tax-exclusive bases must never be mixed. Sources must return currency and timestamp; UI shows stale/incomplete indicators where appropriate.
## 8.3 Async and external system behavior
Use an outbox in the transactional owner system and bounded retries with jitter and dead-letter review. Adapter event processing must be idempotent and observable. Cross-service data is eventually consistent; do not show financial success before ERPNext confirms posted document. Provide reconciliation jobs comparing IDs, checksums and amounts, and an operator repair path.
## 8.4 Offline PWA
Store only minimum local draft site data, never long-lived secrets or full financial records. Use IndexedDB with versioned schema, draft IDs and an outbox; display pending/synced/conflict/failed state. On reconnect, revalidate role, project, attachment and duplicate key. Photo uploads support retries and compression; submit only after acknowledgments. No offline approval, GL posting, PO release or payment settlement.
# 9. Source reuse and merging discipline
## 9.1 Preferred approach
Fork BuildSuite in a controlled vendor branch; pin upstream SHA; keep VORQ custom code in separately versioned Frappe app and limited frontend extension layer. Branding and navigation customization should be layered through shared tokens, not blanket upstream changes. Use ERPNext Desk for specialist accountants/admin instead of rebuilding every screen.
## 9.2 Cepho porting workflow
Extract specific IPC / retention workflow rules and tests as a reference; verify law and accounting semantics; implement equivalent v16-compatible DocTypes/hooks in VORQ custom app; regression test against BuildSuite and standard ERPNext documents. Do not merge arbitrary hooks, DB migrations or duplicate BOQ DocTypes.
## 9.3 OpenProject integration gate
Only if real clients need features missing from BuildSuite scheduling. Map canonical project/task and dependency IDs; OpenProject stays an optional service with its own DB; avoid simultaneous write authorities. API v3 is not complete for every UI operation, so spike the exact required endpoints first.
## 9.4 OpenConstructionERP integration gate
Review actual repository components and third-party attributions; decide commercial license vs AGPL-compatible distribution before copying/embedding frontend. Keep FastAPI/PostgreSQL service separate. Imported quantity data is unapproved until QS reviews units, geometry, classifications and rates. For frontend, a routed module with common header and SSO is preferable to a raw unauthenticated iframe; visual integration does not eliminate license or security obligations.
# 10. Deployment and operations
Environments: local reproducible development, synthetic-data staging, isolated production tenant sites. Never import real customer data into public demos.
Provisioning: create site/database, configure domain/TLS, install pinned apps and fixtures, establish private storage, tenant admin and sample data where authorized.
Backups: encrypted database + file backups, scheduled integrity checks, restore rehearsal to a fresh isolated site. Specify pilot RPO <=1 hour / RTO <=8 hours as proposed engineering goals only after proving infrastructure can meet them.
Observability: request IDs, server errors, queue depth, sync backlog, backup health, ERP post failures, security denies and p95 page/API timing. Log IDs, not personal sensitive payloads.
Releases: dependency lock update in sandbox, migration dry-run, accounting reconciliation fixture, canary tenant, rollback/restore plan, then rollout. Never upgrade ERPNext on all tenants blindly.
Data export: tenant owner can request project, invoice, BOQ and attachment export in agreed open formats; document limits and any ERP-specific dependencies.
# 11. Threat model and quality gates
Threat / failure	Mandatory control / test
Cross-tenant or cross-project leak	API negative tests for list, filter, export, attachment and direct IDs
Duplicate invoice on retry	Unique source-target link, race simulation, replay and cancellation test
Unauthorized approval	Backend permission checks + approval history, not frontend-only route guard
Malicious file	MIME/extension check, size limit, malware scan, private attachment ACL
CSRF / session fixation	Framework controls, HttpOnly/SameSite cookies, token rotation, security headers
XSS in notes / file names	Escape content, forbid unsafe HTML rendering, CSP and automated tests
Silent stale reporting	As-of time, data quality flag, source drilldown and alert
Offline conflict	Revision handling, explicit conflict UI, never last-write-wins on approved records
Migration loses GL consistency	Pre/post reconciliation totals, schema backups, rollback route

# 12. CI/CD and test plan
Static: Python lint/type checks as supported, Vue/TypeScript lint, dependency license/security scan, formatting.
Unit: BOQ totals, retention/advance waterfall, cost mapping, UOM conversions, rate change, maker-checker policies.
Integration: ERPNext PO -> receipt -> issue, bill -> ledger, invoice -> receivable, cancel/amend reversals, source event idempotency.
Contract: Frappe API schemas and optional adapter payloads; versioned fixtures detect upstream changes.
E2E: role login, project creation, approved BOQ, daily report, stock receipt/consumption, bill, owner dashboard drilldown; responsive and accessibility checks.
Regression: version-pinned releases and migration snapshot, financial parity and negative project/tenant access tests before each customer upgrade.
No module is accepted if it only passes UI tests while resulting accounting documents are incorrect. Staging smoke test alone is not production validation.

# 14. Implementation sequence and detailed exit criteria
Inventory exact DocTypes, routes, Vue component tree and test coverage in pinned BuildSuite revision; identify mock/dead role pages. Exit: code map and known gaps approved.
Reproducibly install Frappe/ERPNext v16 + BuildSuite + compatible India Compliance; record migrations and baseline reconciliation. Exit: clean install twice.
Define canonical IDs, role/project permissions, approved BOQ and project financial snapshot contract. Exit: negative permission tests and ledger fixture pass.
Reuse and polish existing BuildSuite screens for project, BOQ, materials, subcontract and site. Exit: single shell, tokenized UI, no dual entry.
Add PWA offline drafts for site reports; add warning, retry and conflict UI. Exit: field tests on intermittent mobile network.
Pilot customer deployment with monitoring, backups and accountant certification. Exit: paid pilot with first completed business cycle.
Implement advanced client IPC/RA and optional scheduling/takeoff only after demand, licensing and version gates.
